# retire the old AI-first flow

> reachy-mini-cli is a symbolic robot runtime: the robot's presence is the behavior engine driven by rules and configuration, not a hardcoded AI app. Cognition is optional and external — no LLM call happens inside the CLI's presence loop.
> instruction: Deliver as a PORT-THEN-DELETE sequence, one capability per PR, each live-verified on the deployed robot before the next: (1) speech actuator on a background worker; (2) sound-orienting as a runtime goal; (3) hearing words as a transcript sense; (4) rms + face + frame_available providers over a held client; (5) shipped default rules.toml + the dormant-predicate warning; (6) ONLY THEN delete the think noun, the listen --live composition root and the listen noun, re-homing forge onto 'agent attach' and the expressions catalog onto a surviving noun. Verify with the import-boundary test and the offline lane (h1).

## Audience

- Three consumers, in priority order: (1) the OPERATOR running a Reachy Mini as a persistent presence, who wants behavior they can change by editing configuration rather than by editing Python; (2) the CONTRIBUTOR, who today must reason about two overlapping presence loops with different sense paths, motion queues and failure modes; (3) an ATTACHED AI AGENT, human, or script — all three consume the same runtime feed + intent spool, which is issue #70's 'robotic capabilities should be available to humans, scripts, symbolic systems, and AI agents equally'.

## Before → After

- Before: Today two presence loops coexist and compete. The AI-first one ('listen run --live --transcribe --cognition agent --voice-engine harmonic', still the LIVE_UNIT ExecStart at units.py:101) folds think/vision/sleep/face/scene/pat/transcribe hooks into one process and needs a reachable LLM endpoint to do anything expressive — the robot's personality is a prompt plus 1083 LOC of think.py, and its reactions cost tokens and round-trip latency. The symbolic runtime ships alongside it and is already the boot presence on the deployed box, but is comparatively mute, deaf to words, and configured by a rules.toml that no install provides.
- After: reachy-mini-cli has exactly two presence owners, both CLI-selected: 'demo-mode' (the simple idle loop) and 'behavior' (the symbolic runtime). The runtime can see (doa/pat), hear words, speak, and orient — every capability the retired flow owned — and what it DOES with them is declared in a shipped, editable rules.toml, not compiled into a command module. No LLM call happens anywhere inside the presence loop; cognition is opt-in and external via 'agent attach', which reads the runtime feed and writes symbolic intents.

## Why it matters

- Issue #70's case, now evidenced by this repo's own history: deterministic embodiment should not cost tokens, latency, or network availability. A robot that needs an LLM round-trip to react to a head pat is expensive, slow, untestable offline, and tightly couples embodiment to cognition. Keeping BOTH flows is worse than either: two presence owners contend for the single SDK client and the single MotionQueue (the single-SDK-owner model), capabilities drift between them, and every new feature must be built twice. The old flow's continued existence is now the main source of that duplication.

## Decisions

- VOICE DEFAULT IS HARMONICS (Ori). The runtime's speech actuator uses reachy/speech/harmonic.py — the in-process, offline note-melody synth backed by harmonics-cli, a BASE runtime dependency with zero transitive deps — as its DEFAULT. TTS (reachy/speech/tts.py, the Chatterbox HTTP leg) is CONFIGURABLE, not the default. This substantially defuses the tick-budget risk: the default path is an in-process import with no network round-trip, so the only blocking cost is device-bound playback rather than an HTTP synthesis call. It also means a fresh box with no reachable service speaks out of the box, which is what makes h9 ('a fresh install reacts with NO operator-authored configuration') achievable for voice as well as motion.
- LIVE VERIFICATION of t27/t28's tick-stall fix, on the deployed robot 2026-07-20 ~19:32-19:36 IDT. A/B on the same hardware minutes apart. BRANCH build (foreground, unit stopped, 1500 ticks): setup order was 'connected (media_backend=no_media)' then '[SENSE stage=warmup source=state event=setup] warmed before the first tick' then '[behavior] engine live' — construction completed BEFORE ticking — and ZERO overruns across 1500 ticks. INSTALLED build (0.41.0, no fix), on the two restarts performed during the same session: overrun tick=447 duration_ms=913.18 and overrun tick=446 duration_ms=699.62, both against the 20 ms budget. This closes t27 acceptance criterion 2, which was built but explicitly unverified, and confirms c38's diagnosis (lazy client construction on the tick thread) was correct.
- t6 chose the http playback transport because the sdk path was ECONNREFUSED at the time it decided. That diagnosis has since advanced: #94's root cause is that the daemon RELEASES the media subsystem when no consumer holds it, and POST /api/media/acquire makes a media client construct in 0.9s. So the sdk path is reachable after all, once t30 wires acquire. t6's choice still stands on its other two grounds — the daemon already owns the speaker so routing through it is single-owner-consistent, and it needs no [sdk] extra, the same property that made harmonic the default voice. The transport is injected and env-overridable (REACHY_SPEECH_TRANSPORT), so this is a default, not a lock-in.
- COOLDOWN VERIFIED CORRECT — retraction of a live-session suspicion. The 2294-admissions-in-5-min count conflated journal MENTIONS with fires: the same journal window shows 42 fired / 5414 drop reason=already-active / 1308 drop reason=cooldown for look-toward-sound — exactly the designed already-active-then-cooldown gating. rule_engine.py cooldown/hysteresis logic is a BOUNDARY for the fix wave: do not touch it. Residual real finding: per-tick drop lines flood the journal — emit a drop reason once per TRANSITION (episode), not every tick, keeping the senselog a-drop-always-names-its-reason grammar.

## Hard questions

- risk: Audio is the first genuinely BLOCKING side effect in a loop whose entire correctness argument is tick-budget determinism. Synthesis is a network round-trip (Chatterbox, ~24 kHz PCM over HTTP) and playback is device-rate-bound. If the off-thread boundary is drawn wrong, the symptom is not a crash but tick overruns — i.e. visibly degraded motion — which is exactly the property the symbolic runtime was built to guarantee.
- risk: Hearing needs a microphone, which means the runtime process must open the SDK media session — a resource the single-SDK-owner model says has exactly one consumer. The runtime already holds an SDK client for pose read-back (HeldStateReader). Getting audio and pose from ONE held client is a design constraint, not an implementation detail; two clients reintroduces the ~1 Hz throttling that motivated folding senses in #43.
- risk: The runtime process becomes the single media consumer. reachy/robot/state_reader.py:29-31 already anticipates this — it documents that a runtime process also needing media should hold ONE no_media pose client AND one media client, never sharing them — so the shape is designed, not novel. But two lifecycles now need explicit close(): state_reader.py:20-24 warns the process HANGS at interpreter exit unless the client is explicitly closed, and the media client adds a second such handle. Getting mic (c11), rms (c21) and camera frames (c21) from that ONE media client is what makes the port safe; a second media client reintroduces the ~1 Hz throttling that motivated folding senses in #43.
