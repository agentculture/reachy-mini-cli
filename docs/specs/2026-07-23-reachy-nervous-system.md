# reachy nervous system

> Reachy's nervous system ships: vision, hearing and voice all work on the deployed robot (issues 94/97/120/121/122 resolved), and the runtime exposes its senses and media - camera frames, mic audio, DoA, sense events - on an event-based surface other services subscribe to, so a heavy sense never slows the 50 Hz tick and no consumer ever contends for the single SDK session
> instruction: deliver as one arc: the five issue dispositions first (each independently landable), then the MQTT nervous-system leg; every headline capability live-verified in ONE acceptance session on the deployed box, driving the robots hearing with monitor-speaker TTS (c30) so the session is automatable

## Audience

- the person in the room (the robot sees them, hears them, and answers aloud again); the operator (a dead sense is visible in doctor and state.json, the journal is greppable again, one broker to tail for everything); and EXTERNAL services — first the reTerminal panel, later tau and daria — subscribing to Reachys senses over the broker without touching the SDK

## Before → After

- Before: the robot is mute on a measured-false premise (box tombstone on greet-when-addressed); the face sense was dead since install with one latched boot line as the only evidence; the journal floods at 39 overrun lines/s, burying real events and timing out greps; #94s stale premise still props up wrong doc claims; and the only external-consumer path is one stdout pipe (--export -) that exactly one process can read
- After: vision, hearing and voice all work on the deployed robot; the five issues are dispatched (#120/#121/#122 fixed, #94 closed as stale, #97 rescoped); the runtime publishes sense/rule/intent/motion events and retained state to a local MQTT broker with graceful no-broker degradation; the reTerminal bridge renders from the broker instead of a single stdout pipe; a 30-minute journal carries tens of overrun lines instead of seventy thousand; a missing [vision] extra is visible in doctor and state.json instead of one boot line

## Why it matters

- a sense that fails silently erodes trust in every sense, and a robot whose senses are locked inside one process is a dead end for the ecosystem around it — publishing the nervous system turns one robot into a shared sensor-and-actuator platform other agents (reTerminal, tau, daria) build on, which is the reachy_nova idea done properly on the symbolic runtime

## Scope / boundaries

- the single-SDK-owner model holds: any media or sense fan-out happens INSIDE the one process that already holds the media session (or the daemon that owns the devices) — no design may open a second SDK media session per consumer.
- in-process fan-out stays nova-shaped: ONE owner pulls each frame/audio chunk, consumers receive copies via throttle-interval + busy-flag + background daemon thread, and no consumer ever re-opens the hardware — the pattern reachy-mini-cli already uses (AudioPump/_AudioTap, face worker) and must not regress.
- there is NO server code in reachy-mini-cli today — realtime_wire.py is client-side-only RFC 6455 by design, no listening socket anywhere — so any fan-out server is wholly new code; and camera+audio never travel the daemon FastAPI surface at all (no frame route exists upstream; media rides a separate GStreamer webrtcsink signalling server with a single-consumer session), so raw-media exposure cannot be a daemon HTTP addition from this repo.
- the broker does not copy novas recorded weakness: mosquitto binds localhost by default and anonymous access beyond loopback is off — novas checked-in allow_anonymous-on-LAN config is cited as the anti-pattern; remote consumers get an explicit, documented opt-in.
- media NEVER travels over the event bus — events carry only TEXT REFERENCES to media: file locations, or better, memory links (Unix-domain-style handles). This governs v1 and every future raw-media leg: frames/audio move out-of-band, the bus only announces where they are (user correction, 2026-07-24).
- regardless of reuse-vs-replace, the arc leaves exactly ONE broker on the box and it satisfies c23: the compose port mapping is EXPLICITLY 127.0.0.1:1883:1883 because Docker publishes on 0.0.0.0 by default AND its NAT bypasses host firewalls (the live nova broker demonstrates the anti-pattern right now); challenge pass / security lens: docker ps + ss -ltn probe 2026-07-24
- the MQTT leg is ADDITIVE: the --export stdout contracts (runtime feed and cognition feed) and the agent attach --feed path are byte-identical after this arc — a consumer of the old surface never notices the new one exists
- reachy/state/* retained payloads MIRROR the state.json payload from the ONE existing builder — never a second derivation that can drift; the topic tree is a transport for the same truth, not a new source of it
- build discipline for a box that RUNS the working tree: the deployed runtime executes this checkout via the editable uv tool install, so a systemd restart picks up whatever branch is checked out — fan-out lanes stay in worktrees, the main checkout stays on a known-good branch during the build, and every live-verify step names the branch the box is running

## Decisions

- the MONITOR speaker is exempt from Reachys internal AEC — only the robots own speaker channel is cancelled. Playing synthesized speech through the monitor speaker is therefore a valid, automatable way to SPEAK TO Reachy: hearing tests (#122 verify, acceptance sessions) can drive the robot with TTS out the monitor instead of requiring a human voice (user correction, 2026-07-24).
- the c16 threading question resolves PROBE-FIRST (user decision 2026-07-24): a short live probe during the #122 verify session establishes whether push_audio_sample tolerates the speech worker thread; the injection shape (direct vs pump-style output seam) is decided on that evidence, and the probe is a named plan task
- the broker is EXPORTED to events-cli (user decision 2026-07-24, amending q6): reachy-mini-cli ships NO compose and never operates the broker — it consumes REACHY_MQTT_URL (default localhost:1883) exactly as it consumes the lobes gateway and STT/TTS services; our consumer requirements (direct MQTT port access, loopback bind, retained+LWT+QoS0, nova-stack replacement on the box) are filed as events-cli#3 so the two arcs parallelize; the q7 nova-replacement executes inside events-cli deploy, not this repos plan
- the publisher client is EVENTS-CLI THE PACKAGE, imported (user decision 2026-07-24, amending q5 and superseding c38): reachy-mini-cli never depends on paho-mqtt or any MQTT library — it imports the events-cli client surface, and the transport under it (paho or a complete no-deps rewrite) is events-cli internal concern once it left our repo (recorded on events-cli#3 comment). The base dep becomes events-cli (pure wheel, py>=3.12, first published release is the composition unblock; uv lock rides the same change); the publisher codes against an injected client seam so tests fake it and the real import binds in one composition line
